## 0. 一页结论

- **产品形态**：纯手机 App（iOS/Android 概念），不做桌面网页版，不依赖智能冰箱硬件。
- **一句话定位**：*Know what's in your fridge — without a smart fridge, and without typing.*（不用买几千块的智能冰箱，也不用打字，就能知道冰箱里有什么、什么该先吃。）
- **设计原则**：少而精。只做 3 个核心功能 + 1 个可选功能，每个都做到"谁都能用、一看就懂"。不追求功能全覆盖，避免 Vibe Coding 式的大杂烩。
- **核心卖点**：零文字输入（自动读电子小票 / 拍一张照 / 一句语音）+ 不用每顿都打开 App（无声提醒、桌面小组件、睡前 10 秒复盘）。
- **交付物**：3 分钟概念视频 + 2 页报告，**10/20（周二）15:00** 截止。不做任何真实技术实现（无后端、无 API、无服务器），只做设计概念与展示：User group → Pitch → Lo-fi → Hi-fi → 可点击前端展示。
- **视频方向**：两个 persona 各讲一个短场景（John、May），真人实拍 + App 界面展示 + 动态文字卡；AI 卡通动画最多占 30–60 秒，不贯穿全片。

## 2. 研究依据（不能新增或编造发现）

### 6 个发现（F1–F6）与本次设计的直接回应

| 发现 | 关键证据（报告原文） | 本次设计回应 |
|---|---|---|
| F1 非正式库存追踪 | 靠记忆和开冰箱看；在外面看不到家里（P2）；东西被埋在底下（P2） | 虚拟冰箱：出门在外也能"打开冰箱看一眼" |
| F2 记录太费劲 | 每样都拍照不现实（P2）；详细记录会变成负担（P6）；P6 只在用完最后一点时记一次 | 零文字录入；一次购物只需一个动作；不要求完美记录 |
| F3 新鲜度判断 | 蔬菜没日期（P1）；日期磨掉（P2）；分袋后标签靠手贴（P3）；解冻后发酸（P3） | 自动带日期；分袋自动继承冷冻日期；估计日期用虚线明确标注 |
| F4 计划随日程变 | 出去吃、太累、考试周（P1、P2、P3、P6、P8） | 一键"今晚不在家吃"，自动重排先用顺序；不强迫做计划 |
| F5 合租协调 | 分不清是谁的（P7）；被用掉不知道（P8）；重复购买不一定是错（P5） | 个人/共享分开；室友的东西只显示数量；不记录谁吃了共享食物 |
| F6 储存空间 | 没冷冻室只能买两天（P4）；抢冰箱空间（P5）；放不下（P6） | 虚拟冰箱上直观看到每层多满；没冷冻室的用户（May）冷冻区不出现 |

### 5 条功能需求（R1–R5）+ 伦理需求（E）
R1 低负担录入且可修改 · R2 按位置管理、到期提醒、估计要标明不确定 · R3 计划变了能快速调整并重排 · R4 个人/共享区分与合租协调 · R5 储存容量可见 · E 只与授权住户共享、连接零售数据须明确同意、估计可审可改、不变成室友互相监视。

## 3. 竞品与 Gap

| 类型 | 代表 | 能做什么 | 问题 |
|---|---|---|---|
| 智能冰箱 | Samsung AI Family Hub（澳洲 2024 上市，JB Hi-Fi 标价约 A$5,399） | 内置摄像头 AI Vision Inside 识别放进/拿出的食物；SmartThings App 远程看清单、到期提醒；早年 Family Hub 曾接入 Woolworths 下单 | 只认约 33 种生鲜，**要一件一件扫**；门架和冷冻室识别不了；use-by 日期要手动设；租房学生不可能换冰箱 |
| 智能冰箱 | LG InstaView ThinQ 等 | 屏幕、摄像头、语音助手 | 同样贵、绑定硬件，合租冰箱不归个人 |
| 食物库存 App | NoWaste、KitchenPal、Fridgely、Fridgi、Kitche 等 | 条码扫描、手动录入、到期提醒、部分有拍照识别 | 基本是**一件一件录**，正是 F2 说的负担；多数要频繁打开 App；合租隐私考虑少 |
| 食谱 / 营养 App | Samsung Food 等 | 菜谱、营养、膳食计划 | 偏健康管理，偏离"管食物"本身 |

**Gap（我们的位置）**：智能冰箱的"全自动"体验，用一部手机实现到"够用"的程度。
1. 不靠硬件：录入发生在**购物那一刻**（电子小票 / 一张照片），而不是靠冰箱摄像头时刻监视，因此也没有"家里有摄像头"的隐私问题。
2. 不靠频繁打开：被动提醒 + 桌面小组件 + 睡前一句话复盘，替代"每顿饭都开 App 记账"。
3. 为合租设计：同一个冰箱、不同主人，信息只给协调所需的最小量。

> 与市面产品部分重合没关系：课程不考察商业差异和技术可行性（Jenny 10/6），只要不科幻、能对应 fieldwork 即可。

## 4. 产品定义

### 4.1 目标用户
在澳洲生活的大学生（18–26），工作日忙、计划常变；包括一个人住有冷冻室的批量采购型（John）和合租无冷冻室的高频少量型（May）。

### 4.2 核心功能（只做这些）

| # | 功能 | 用户做什么 | 系统做什么 | 需求 |
|---|---|---|---|---|
| **C1 零输入录入** Capture | 三选一：① 首次授权后，超市电子小票自动进来；② 纸质小票或购物袋拍一张；③ 实在不方便时说一句 | AI 识别成食物卡片，自动带上日期和存放位置；肉类可"分成 N 袋"一键拆分并记冷冻日期；用户**一键全部确认**，有疑问的单独点一下 | R1 R2 E |
| **C2 虚拟冰箱** Virtual Fridge（首页） | 随时打开看，在超市、在公交站都行 | 冰箱/冷冻室/橱柜可视化，食物用图片不用文字列表；越该先吃越靠前；估计日期用虚线；室友的东西显示为"3 items from housemates"；每层显示多满 | R1 R2 R4 R5 E |
| **C3 无声提醒** Quiet Nudges | 什么都不用做 | 只在真正需要时推一条（例："Beef mince, bag 3 — frozen 4 weeks. Use this week?"）；通知上直接点 *Ate it / Not today / Moved to freezer*；有免打扰时段，同一天的提醒合并成一条 | R2 R3 |
| **C4 一下就更新** Quick Update | ① 桌面小组件点一下 −1；② 晚上对手机说"今天吃了两袋牛肉和番茄炒蛋"；③ 计划变了点"Eating out tonight" | AI 解析语音并扣除对应食物，给出变化清单让用户确认；计划变了自动重排先用顺序 | R1 R3 |
| 可选 **O1 下周计划 & 购物清单** | 想要才开（默认关闭） | 基于冰箱里已有的东西生成简单清单；合租可共享清单 | R3 R4 |

O1 的定位（Raina 原话，可直接用作旁白思路）：*If users want to make a detailed plan for their food management, they can also use the planning function. It's completely optional, as we don't want to add extra pressure or cognitive load.* 依据：F2（不想详细记录）+ F4（计划常变）+ 报告 UX 需求"不要让用户觉得必须维持完美记录或严格计划"。

### 4.3 明确不做（及理由）

| 不做 | 理由 |
|---|---|
| 卡路里 / 营养 | 难以准确计算；会把产品推向健康管理 App；fieldwork 里没有这一需求 |
| 食谱推荐 | 不是 6 个发现的核心；做不好会稀释卖点。未来工作可提一句"用先过期的食物出菜" |
| 待办清单 / 提醒事项 | 用户已有系统备忘录和 Reminders，重复造轮子 |
| 室友空闲时间匹配、谁去买的分工 | 过重；R4 用"共享清单 + 室友物品只显示数量"已足够回应 |
| 拍照估计冰箱容量 | 不准且涉及拍到室友食物；改为虚拟冰箱上按已记录物品显示的粗略占用 |
| 桌面网页版 | 先假设纯手机 App |
| 智能冰箱联动 | 放进"未来工作"：若用户已有带摄像头的冰箱，可作为额外数据源 |

### 4.4 隐私与伦理设计（视频轻提，报告详写）
- 读邮箱：只读用户勾选的超市寄件人（如 Woolworths、Coles 的电子小票），只提取商品行，不读其他邮件、不读付款信息；可随时断开。更窄的替代方案：把小票转发到专用地址。
- 照片和语音在手机端处理，原图不上传、不保存。
- 不需要真名；登录用 Apple / Google 一键登录，只为跨设备同步。数据默认存本机，合租组只同步标为"共享"的物品。
- 估计日期一律标为估计（虚线 + "estimated"），不当成食品安全保证。
- 合租：不记录谁吃了共享食物，不出现"某某用了你的牛奶"之类的推送。

### 4.6 小组件（Widget）与虚拟冰箱视觉（2026-10-09 补充，Raina 决定）

**定位**：小组件不是新功能，而是 C2 / C3 / C4 的"出口"。目标是用户不打开 App 也能看到冰箱，这是"解放双手、免打开"的主要载体，也是视频里最有辨识度的画面。核心功能仍是 C1–C4（+可选 O1），范围不扩大。

| 小组件 | 尺寸 | 内容 | 对应 |
|---|---|---|---|
| 虚拟冰箱 | 大 | 冰箱剖面图，食物用真实图片按层摆放，最该先吃的带琥珀色角标 | C2 |
| 当前食物 | 中 | 文字列表：名称 + 存放位置 + 剩余天数 | C2 |
| 即将过期 | 小 | 2–3 项，点一下直接 Ate it / Not today | C3 C4 |
| 购买计划 | 小 | 可选，默认不出现 | O1 |
| 锁屏 | 锁屏小组件 | 只显示一个数字或一个小图标："2 to use soon" | C3 |

- 概念阶段可以这样讲：小组件在后台自动刷新，交互式小组件允许直接点按钮更新库存。实际系统会限制刷新频率，不是实时的，这一点写进报告的局限部分，不进视频。
- 视频里用高保真截图合成桌面画面，不需要真的做出小组件。

**虚拟冰箱界面方向**（参考图为收集用，不直接使用，三星等品牌画面和第三方设计不进入成品）
- 干净的白色冰箱内部作为底：白色为主，浅灰搁板线，绿色只做点缀（主按钮、状态、少量强调）。
- 每层搁板上是格子，食物用抠图实拍图（统一光影、柔和投影），不用 emoji，不用卡通混搭。
- 防杂乱：同类合并成一格（如"Beef x6"）；室友的东西合并成一格"3 items"；一屏不超过约 12 个图标。
- 冷冻室用同样结构，加冰霜边缘和日期角标；May 没有冷冻室就不显示。
- 食物图片来源要可商用或自己拍（自己买一轮菜拍，最稳）。

### 4.7 Persona 场景细化（2026-10-09，Raina 决定）

- **John（一次买很多、冷冻室很大）**：一整袋牛肉末、一盒 4 块的鸡腿肉。App 根据他以往的习惯建议拆分（"Split into 5 bags?"），拆完每袋是一张独立的卡片，继承冷冻日期。冷冻室大，旧的容易被埋，所以重点是先用最旧的那袋。展示：C1 录入 + C3 提醒 + 一点更新。
- **May（天天买、存储不是主要问题）**：她的问题是共用冰箱和计划被打乱。展示：在超市打开虚拟冰箱看家里有什么（室友的东西只显示数量）+ "Eating out tonight" 一键重排 + 睡前语音复盘。容量问题不是她的主线，最多一笔带过。
- 视频不演示"重复购买警告"：概念里没有购物清单，也没有可靠的方法知道她正要买什么。该点只在报告里作为 R4 的扩展方向。

### 4.8 制作顺序（2026-10-09 决定）
故事板先于视觉规范：故事板决定需要哪些屏和哪些状态，视觉规范只需覆盖这些，不会多做。顺序为：故事板 v1 → 视觉规范 → Figma 低保真 → 高保真 → 组员 AI 出展示动效 → 拍摄与剪辑。拍摄日期（10/12 或 10/15–16）依赖故事板，所以它是关键路径。故事板见《Eat It - Storyboard v1》。

## 5. User Flow（最短版）

```
1 买回来 → 录入        小票自动进来 / 拍一张 → 一键确认 → 出现在虚拟冰箱
2 出门在外 → 看 + 提醒  公交站打开虚拟冰箱；肉快到期时收到一条无声提醒
3 吃掉了 / 计划变了     小组件点一下，或睡前一句话；"今晚不在家吃" → 自动重排
(4 可选) 下周计划       想用才打开；基于已有食物生成清单
```

首次使用（onboarding，3 步，可跳过）：选存放位置（冰箱 / 冷冻室 / 橱柜）→ 一个人住还是合租（合租可邀请室友）→ 是否连接电子小票。

### 5.1 高保真页面清单（约 13 屏）

| # | 页面 | 对应 |
|---|---|---|
| 1 | Welcome / 一键登录 | 登录 |
| 2 | Onboarding：存放位置 + 住法 + 连接小票（3 步） | 首次设置 |
| 3 | 小票授权同意页（读什么、不读什么） | E |
| 4 | 虚拟冰箱首页（John：冰箱 + 冷冻室） | C2 |
| 5 | 虚拟冰箱首页（May：合租、无冷冻室、室友物品数量） | C2 R4 |
| 6 | 录入入口（中间大按钮）：拍照 / 语音 | C1 |

## 6. 视频方案（3:00）

> 2026-10-09 更新：本节的分镜骨架已被《Eat It - Storyboard v2》取代。v2 是 12 段、节奏更慢、开头为纯文字 hook；以 v2 为准。


### 原则
- 两个 persona，各一个短场景、各一个清楚的目标，用一个转场连接（例："On the other hand, May…"）。依据：作业说明的结构写的就是 *Introducing persona(s)* 和 *Use case scenario(s)*；评分看的是"某人用它完成一件有意义的事"是否清楚，两个场景只要各自目标清楚就不违反 Jenny"讲一个场景"的建议，反而能显示考虑到不同住法。
- 每个画面短，节奏快；讲概念和理由，不逐个讲界面。
- 真人实拍为主（朴素即可，手机拍、稳、收音清楚），配 App 界面展示和动态文字卡。不用 AI 生成真人，不用 AI 配音；用组员自己的声音 + 字幕（Jenny 10/6）。
- AI 卡通动画最多 30–60 秒，只用在开头问题蒙太奇或过渡，且不能和实拍混得太碎。
- 旁白台词和报告正文由组员自己写（课程 AI 规定），本文只给结构与要点。

## 7. 视觉方向（详细视觉规范另出）

- **基调**：纯白底 + 浅绿色（参考图：生鲜/健康类 App 的白底、浅绿卡片、深色粗字号数字）。干净、留白多、信息少。
- **初拟 Token**（待在 Figma 里校准对比度）：

| Token | 值 | 用途 |
|---|---|---|
| `bg` | #FFFFFF | 页面背景 |
| `surface` | #F4F6F1 | 卡片底 |
| `green-200` | #DDF0C4 | 浅绿强调卡 |
| `green-500` | #8BC34A 附近 | 主色、主按钮、进度环 |
| `ink` | #16200F | 主文字、大数字 |
| `muted` | #6B7465 | 次要文字 |
| `use-soon` | 琥珀色 | 快到期 |
| `urgent` | 克制的红 | 今天必须处理（少用） |

- **字体**：一款几何圆润无衬线（候选：Plus Jakarta Sans / Manrope / Outfit），大数字加粗；英文界面。
- **形状**：卡片圆角 20–24，主按钮胶囊形，中间一个圆形录入按钮。
- **食物表现**：统一风格的食物图片（实拍抠图或统一插画），**不用 emoji**；首页以图为主，不是表格。
- **状态语言**：包装日期 = 实线标签；估计日期 = 虚线标签 + "est."；冷冻 = 雪花小标。
- **禁止**：渐变堆叠、玻璃拟态、紫色、多彩标签、密集文字表格、AI 生成真人。

## 8. 分工与 AI 使用规则

| 角色 | 人 | 职责 |
|---|---|---|
| 设计负责人（定规则） | Raina | 产品定义、flow、视觉规范、Figma lo-fi → hi-fi、给组员 AI 写交接规范、最终审美把关 |
| 生成执行（额度多） | 做动画的组员 | 按 Raina 的交接文档，用高级模型生成：展示前端 / 动效 / 文字卡动画 / 必要的少量动画片段。**不自行扩功能、不改视觉** |
| 拍摄 / 出演 / 剪辑 | 待周五会议分配 | 按第 6 节分镜 |
| 报告 | 全组 | 2 页：概念 + 功能-需求对照、伦理与非预期使用、未来评估 |

给组员 AI 的硬规则（详细 handoff 另写）：
1. 先读本文，再动手；一次只做一个明确的产出（一屏或一段动效），不要"全部重做"。
2. 只做第 4.2 节列出的功能和第 5.1 节列出的页面；不做桌面版，不加第 4.3 节"不做"的东西。
3. 颜色、字体、圆角只用第 7 节（及之后的视觉规范）的 token。
4. 前端只在 Figma 高保真定稿后开始，按 Figma 还原，不自由发挥。
5. 不生成真人、不生成 AI 配音、不编造参与者数据或新发现；旁白和报告正文由组员自己写。
6. 每次产出先给 Raina 看截图，确认后再继续，避免浪费额度跑错方向。
